# Tailwind Design System Migration

**Date:** 2026-05-11
**Status:** Approved
**Approach:** Layered migration (3 phases)

## Goal

Replace the 1116-line `globals.css` with a clean, Tailwind-native design system. Consolidate color tokens to shadcn naming, register animations in Tailwind theme, delete dead code, and inline all custom CSS classes into components as Tailwind utilities.

## Current State

The existing `globals.css` has two parallel token systems that must be merged:

1. **Custom tokens** (lines 14-117): `--bg-page`, `--text-1`, `--accent`, etc. — defined in hex/rgba
2. **shadcn tokens** (lines 88-117, 842-874): `--background`, `--primary`, `--card`, etc. — defined in oklch

Both coexist in the same `:root` block. The oklch shadcn tokens were auto-generated by shadcn init and are not the design source of truth — the custom hex values match the actual design spec from CLAUDE.md. **This migration replaces the oklch values with hex values** because the custom tokens represent the intentional design choices, and hex values are more readable and maintainable. There is no visual difference in practice since the oklch values were derived from the same hex values.

There are also two `@layer base` blocks (lines 241-267 and 876-890). The second block (`* { @apply border-border outline-ring/50; }` and `body { @apply bg-background text-foreground; }`) was added by shadcn init and conflicts with the first block's `html, body { background: var(--bg-page); color: var(--text-1); }`. **Phase 1 merges these into a single `@layer base` block** using the consolidated tokens.

## Decisions

| Decision | Choice |
|----------|--------|
| Feature-specific CSS classes | Inline as Tailwind utilities in components (no custom classes in globals.css) |
| Color token naming | Consolidate to shadcn convention (`--background`, `--primary`, `--foreground`, etc.) |
| Color format | Hex/rgba (not oklch) — matches design spec, more readable |
| Hardcoded colors in components | Replace semantic ones with tokens; leave decorative one-offs as arbitrary values |
| Dark mode mechanism | Standardize on `.dark` class (Tailwind-native); drop `[data-theme="dark"]` |
| Animations/keyframes | Register actively-used keyframes in `@theme inline`; delete unused ones |

### 1.6 Merge `@layer base` Blocks

The two existing `@layer base` blocks are merged into one:

```css
@layer base {
  * {
    @apply border-border outline-ring/50;
  }
  html {
    @apply font-sans;
    scrollbar-width: thin;
    scrollbar-color: rgba(0,0,0,0.1) transparent;
  }
  body {
    @apply bg-background text-foreground;
    -webkit-font-smoothing: antialiased;
    -moz-osx-font-smoothing: grayscale;
    font-feature-settings: 'kern' 1, 'liga' 1, 'calt' 1;
  }

  /* Scrollbar (pseudo-elements — can't be Tailwind) */
  ::-webkit-scrollbar { width: 4px; height: 4px; }
  ::-webkit-scrollbar-track { background: transparent; }
  ::-webkit-scrollbar-thumb { background: rgba(0,0,0,0.1); border-radius: 10px; }
  ::-webkit-scrollbar-thumb:hover { background: rgba(0,0,0,0.18); }

  /* Selection */
  ::selection { background: rgba(139,92,246,0.15); color: #111; }

  /* Links & rows */
  a { transition: color 0.1s ease; }
  tr { transition: background 0.08s ease; }
}
```

No duplicate `background` or `color` declarations. The `font-family` comes from Tailwind's `font-sans` which maps to `var(--font-sans)` configured in `@theme inline`.

**Deliberately removed from the second `@layer base` block:**
- `[class*="card"]:hover { border-color: var(--border-hover); }` — wildcard selector that implicitly applies hover to ANY element with "card" in its class name. Components already use explicit `hover:border-border-hover` where needed. Removing this eliminates unexpected side effects.
- `.skeleton { ... }` — custom shimmer skeleton class. Not used by any component; shadcn `<Skeleton>` component handles skeleton UI instead.

### 3.2 Scrollbar Classes

`.sscroll`, `.ac-scroll`, `.chat-scroll` all define custom scrollbar widths. These require pseudo-element selectors.

**Decision:** Consolidate into one `.thin-scrollbar` class in `@layer base`:

```css
@layer base {
  .thin-scrollbar::-webkit-scrollbar { width: 3px; }
  .thin-scrollbar::-webkit-scrollbar-track { background: transparent; }
  .thin-scrollbar::-webkit-scrollbar-thumb { background: rgba(0,0,0,0.1); border-radius: 2px; }
}
```

Replace all `sscroll`, `ac-scroll`, `chat-scroll` references in components with `thin-scrollbar`.

### 3.3 What Stays as CSS (Cannot Be Inlined)

These remain in `globals.css` because they use selectors Tailwind can't express:
- `.float-field:not(:placeholder-shown) ~ .float-label` — sibling selector
- `.thin-scrollbar::-webkit-scrollbar` — pseudo-element
- `::selection` — pseudo-element
- `::-webkit-scrollbar` (base) — pseudo-element
- `input:-webkit-autofill` — pseudo-class with vendor prefix (the `cm-input` autofill hack)
- `[contenteditable]:empty:before` — pseudo-element + attribute selector (compose-ta placeholder)
- `@keyframes` definitions — must be global

### 3.4 Pseudo-Element Handling for `.trow-active`

The `.trow-active::after` pseudo-element (3px accent bar) can be expressed with Tailwind's `after:` variant:

```
after:absolute after:left-0 after:top-0 after:bottom-0 after:w-[3px] after:bg-primary after:rounded-r-sm after:content-['']
```

This does NOT need to stay as CSS.

## Rollback Strategy

- **Phase 1** is safe: aliases ensure zero visual change. If issues found, revert the single `globals.css` + `theme-sync.tsx` commit.
- **Phase 2** should be done in one commit per feature area (academy files, inbox files, supply-chain files, etc.) so individual areas can be reverted independently.
- **Phase 3** similarly: one commit per feature group. Each commit removes the CSS class definition AND updates the component in the same commit, ensuring atomic changes.

If a visual regression is found mid-phase, the relevant feature commit can be reverted without affecting other feature migrations.
